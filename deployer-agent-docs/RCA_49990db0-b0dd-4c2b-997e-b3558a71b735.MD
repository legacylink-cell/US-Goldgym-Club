# RCA — 520 on production /api (usgoldgymclub.com), incl. /api/auth/login

## Summary
The production admin login (and ALL `/api/*` routes) returned a Cloudflare **520** for a window of ~10 minutes. The cause was **not** the application code, the auth logic, routing config, or any secret. It was a **Kubernetes node-drift eviction** of the single serving backend pod, followed by an **abnormally slow (9m26s) container image pull** for the replacement pod. During that gap there was **no Ready backend pod** behind the Service, so the Cloudflare worker that proxies `/api/*` to the k8s origin received an empty/unreachable-origin response and surfaced it as **HTTP 520**. The deployment has since **self-healed** and is serving normally again.

## Scope
- Frontend type: **cloudflare** (static served from R2; a CF worker proxies `/api/*` to the k8s backend).
- Active run: `49990db0-b0dd-4c2b-997e-b3558a71b735` (redeploy, status success — completed 2026-10-16).
- The frontend-only CalendarPage/dialog deploy mentioned in the report is **coincidental** — that run completed successfully on 2026-10-16; the outage began 2026-10-22 02:08 UTC from an infra event, unrelated to that code change.

## Timeline (UTC)
- `01:39:49` — ReplicaSet scaled 2 → 1 (one serving replica remaining).
- `02:08:42` — Serving pod `...-drfgm` **Evicted: "Drifted"** (Karpenter node-drift / node replacement). Container killed.
- `02:08:43` — Replacement pod `...-276jb` scheduled to node `i-07034e0bc62969471`, enters `ContainerCreating`.
- `02:09:02 → 02:18:28` — **Image pull took 9m26s** for the 782MB image (`...@sha256:8136...`). Throughout this window there was **no Ready backend pod** → Cloudflare returned **520** on every `/api` request.
- `02:18:29` — Container started; uvicorn boot began. Startup probe briefly 503 while FastAPI came up.
- `02:18:44` — `Application startup complete`, `Admin account ready for admin@usgoldgym.com`, `Uvicorn running on http://0.0.0.0:8001`.
- After boot — `/api/` returns normal `404 {"detail":"Not Found"}`; `/api/auth/login` (GET) returns `405 Method Not Allowed`. Origin reachable again, **520 resolved**.

- `preview_health_check /api/auth/login` → **405 Method Not Allowed** (route resolves; POST-only — correct).
- `fetch_app_logs` (per-pod, pod 276jb): clean uvicorn startup on 0.0.0.0:8001, admin account ready, no crash/traceback. Earlier logs show healthy 200s on `/api/gcal/events`, `/api/top-program`, `/api/analytics/track` from the prior pod.
- `list_secrets` (active run): `MONGO_URL`, `DB_NAME`, `SMTP_HOST/PORT/USERNAME/PASSWORD`, `JWT_SECRET`, `ADMIN_EMAIL/PASSWORD`, `CORS_ORIGINS` all present and non-empty. Only `STAFF_CC` is empty (optional). **Secrets are correctly bound — not the cause.**
- `get_tier`: tier_0 "Starter", memory_limit 512Mi, cpu_limit 250m, hpa_enabled=false, declared replicas 2. No OOMKilled / exit 137 anywhere — **not a resource-ceiling failure.**

## Root cause
Infra-initiated node-drift eviction of the backend pod, amplified by a 9m26s image pull on the replacement node, left the Cloudflare `/api` origin with no Ready pod → 520. The backend container, FastAPI on 0.0.0.0:8001 behind `/api`, started cleanly once the image finished pulling. MongoDB (MONGO_URL/DB_NAME) and SMTP secrets remained bound throughout.

## Why preview was fine
Preview runs a separate, always-on origin not subject to this k8s node-drift eviction, so it answered `/api/auth/login` with 200 the entire time. This confirmed (correctly) that app/auth code is fine — the fault was production-origin availability only.

## Contributing factors / resilience gaps
1. **Effectively a single replica at eviction time** (ReplicaSet was at 1). With a single pod, a drift eviction = full outage until the replacement is Ready. With ≥2 replicas spread across nodes, drift evictions are rolling and cause no downtime.
2. **Very slow image pull (9m26s for a 782MB image)** on a fresh node turned a brief reschedule into a ~10-minute outage. This is the dominant amplifier and is infra-side (ECR pull throughput / cold node cache).

## Fixes
- **Platform (Emergent) — escalate:** Investigate the node-drift eviction leaving no surviving replica, and the 9m26s ECR image pull. Both are infra. Consider warm image caching / larger surge during drift so the origin never drops to zero Ready pods. (This is an Emergent-side item, not something the user or source can change.)
- **User — verify:** The app has self-healed; retry the admin login at usgoldgymclub.com (hard refresh / incognito to clear any stale CF error page). No redeploy is required to clear the 520.
- **No code fix** and **no secret change** are warranted — backend code, routing, and all MONGO/SMTP secrets are healthy.

## Status
Live and serving as of this investigation — `/api/` returns 200/404 JSON from the backend and `/api/auth/login` resolves (405 on GET, POST path intact).
